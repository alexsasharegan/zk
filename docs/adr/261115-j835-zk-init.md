# zk init makes a box without prompts, and refuses to overwrite

## Context

Starting a box means copying the demo vault's `zk.toml`, hub note and base by hand, then renaming the hub and base and fixing the names inside them. Work item 261115-h674 asks for `zk init` to write them.

ADR 261115-sbpe fixes the command set, and `zk init` is not in it. That ADR is accepted, so this one adds the command rather than editing it.

A box's files are written once and then edited by hand, so a second run must never replace them. ADR 261115-2a31 says zk writes `.obsidian/types.json` only when asked; making a box is asking for one that works. ADR 261115-czb2 opens a terminal UI only when a required argument is missing.

## Considered Options

1. **Ask for the name and folders in a terminal UI.** Friendly, but `zk init` has no required argument, so czb2 would never open it, and the defaults (the folder's name, `cards`, `sources`) are what most boxes want.
2. **Flags for every part of the spec** (`--cards`, `--sources`, `--key-prefix`, field mappings). Complete, but each is one line in `zk.toml`, which the user edits anyway, and a mapping flag would also have to rewrite the base.
3. **A folder and a name only, with defaults for the rest; everything else is edited in `zk.toml` afterwards.**
4. **Register the box in the user config** as well. Saves a step, but zk would edit a file the user owns, and a box found by walking up from its folder needs no entry.
5. **Doing nothing.** Copy the demo vault.

## Decision

Option 3, without option 4.

`zk init [folder] [--name NAME]` makes a box in `folder`, the working directory by default, creating the folder if it is missing. The name defaults to the folder's name. It never prompts. It writes, from the box's default mapping (every field `zk_`):

- `zk.toml`: the name, the hub, the base, `cards = "cards"` and `sources = "sources"`, and an empty `[fields]` table with a comment listing the fields zk can map and an example of each form;
- `<name> Hub.md`: the entrance to the box, with a table of where things are, the commands to work it, and the base's views embedded;
- `<name> Base.base`: an Obsidian base of the cards with the views `All`, `Raw` and `Proposed`, sorted by the sort key;
- the `cards` and `sources` folders;
- the missing property types in `.obsidian/types.json`, through the writer of ADR 261115-2a31, which never changes a type that is set. A type set to something else is reported, and `zk check` then fails on it.

It refuses, writing nothing, when:

- the folder is not inside an Obsidian vault;
- the folder, a folder above it up to the vault, or a folder below it (dot folders such as `.obsidian` and `.git` are skipped) already holds a `zk.toml`, so no box ever holds another;
- `zk.toml`, the hub or the base already exists;
- the name is empty, starts with a dot, or holds a character Obsidian cannot use in a file name or a link (`/ \ : * ? " < > | # ^ [ ]`).

Existing `cards` and `sources` folders are used as they are; nothing in them is touched.

It does not edit the user config. Its output names what it wrote, says to reload Obsidian when it added property types, and says how to make the box the default.

The demo vault's `zk.toml`, hub and base are the files `zk init --name "Slip Box"` writes, and a test keeps them so.

## Consequences

- A new box is one command, and running it twice is safe.
- `zk check` is clean on a new box.
- A box that maps its fields onto the vault's own names must edit the base's field names too: the base is written for the `zk_` names. The comment in `zk.toml` says so.
- The command set is the one in ADR 261115-sbpe, plus `zk init`.
